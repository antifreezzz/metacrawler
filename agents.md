# 🤖 Руководство и правила работы для ИИ-агентов (AGENTS.md)

Данный документ определяет стандарты инженерной культуры, рабочий процесс, правила разработки, тестирования (TDD) и версионирования кода в проекте **Metacrawler**. Все агенты обязаны неукоснительно следовать этим инструкциям.

---

## 1. Роль и ключевые принципы

1. **Senior Go Engineer Mindset**:
   - Писать чистый, идиоматичный, поддерживаемый Go-код (Go 1.24+).
   - Соблюдать принцип наименьшего удивления (Principle of Least Surprise).
   - Не усложнять архитектуру без явной необходимости (YAGNI, KISS).
2. **Честность данных (No Hallucinations / No Fake Data)**:
   - Сервис предназначен для сбора реальных данных. **Категорически запрещено** генерировать фейковые заглушки, выдавая их за результаты анализа (например, выдумывать впечатления блогера, если видео или субтитры не найдены).
   - Если данные отсутствуют — возвращать понятную ошибку, статус отсутствия данных либо честное системное сообщение.
3. **Graceful Degradation (Отказоустойчивость)**:
   - Недоступность внешних API (LLM, Metacritic, YouTube) не должна приводить к падению сервиса (`panic`).
   - Всегда должны отрабатывать локальные алгоритмы (детерминированные эмбеддинги, эвристические выжимки, системные логи).

## 2. Разработка через тестирование (TDD)

Проект строго следует принципам TDD. Код без тестов считается незавершенным.

### Правила:
1. **Red -> Green -> Refactor**:
   - При добавлении новой функциональности или исправлении бага **сначала** создается/обновляется падающий тест (`*_test.go`), воспроизводящий требование или дефект.
   - Реализуется минимально необходимый код для прохождения теста.
   - Проводится рефакторинг с сохранением «зеленого» статуса тестов.
2. **Изоляция и воспроизводимость**:
   - Юнит-тесты **не должны** зависеть от внешней сети или внешних API ключей.
   - Использовать фикстуры, моки и HTML/JSON тестовые дампы (`testdata` или inline константы).
   - База данных в тестах инициализируется в памяти (`:memory:`) или во временной директории (`t.TempDir()`).
3. **Библиотеки тестирования**:
   - Использовать `github.com/stretchr/testify/require` для критических проверок (прерывание при ошибке).
   - Использовать `github.com/stretchr/testify/assert` для некритических проверок.
4. **Обязательный запуск тестов перед сдачей**:
   - Перед завершением любой задачи обязательно выполнить:
     ```bash
     go test -v ./...
     ```
   - Все тесты во всех пакетах должны завершаться с `PASS`.

## 3. Архитектура и организация кода

Кодовая база структурирована по слоям с четким разделением ответственности:

```
metacrawler/
├── cmd/
│   ├── server/           # Главная точка входа приложения
│   └── scraper_probe/    # CLI-утилита для живой проверки скрейпера
├── internal/
│   ├── config/           # Чтение и валидация конфигурации (.env)
│   ├── domain/           # Доменные модели, сущности и контракты (без внешних зависимостей)
│   ├── storage/          # SQLite (modernc.org/sqlite, CGO=0), миграции, репозитории
│   ├── scraper/          # HTTP-клиент (tls-client), обход WAF, парсинг Metacritic
│   ├── llm/              # OpenAI-совместимый клиент, анализ отзывов, эмбеддинги
│   ├── youtube/          # Поиск летсплеев, фильтрация релевантности, парсинг субтитров
│   ├── worker/           # Оркестратор фонового сбора, пагинация, лимиты, SSE-логирование
│   └── server/           # HTTP-сервер, роутинг, хендлеры, FuncMap шаблонизатора
├── web/
│   └── templates/        # Go html/template, Tailwind CSS, HTMX-компоненты
├── Dockerfile            # Multi-stage сборка Alpine (CGO_ENABLED=0)
└── docker-compose.yml    # Окружение развертывания
```

### Архитектурные требования:
- **Чистый SQLite без CGO**: проект использует `modernc.org/sqlite`. Запрещено подключать зависимости, требующие CGO для компиляции сервера.
- **Миграции**: схема БД объявляется декларативно в `internal/storage/sqlite.go`. При изменении схемы необходимо поддерживать обратную совместимость через `ALTER TABLE` / проверку колонок в `migrate()`.
- **Интерфейс и шаблоны**: логика представления выносится в хелперы шаблонизатора (`FuncMap` в `internal/server/server.go`). Не перегружать HTML шаблоны сложными условиями.

## 4. Правила работы с Git и коммитами

1. **Формат сообщений (Conventional Commits)**:
   - `feat(<модуль>): <описание>` — новая функциональность.
   - `fix(<модуль>): <описание>` — исправление бага.
   - `refactor(<модуль>): <описание>` — рефакторинг без изменения функциональности.
   - `test(<модуль>): <описание>` — добавление или изменение тестов.
   - `docs(<модуль>): <описание>` — обновление документации.
   - `chore(<модуль>): <описание>` — обслуживание, обновление зависимостей, конфигов.
   
   *Примеры:*
   - `feat(youtube): add video relevance filter and vtt subtitle parser`
   - `fix(storage): ensure release date sorting takes priority over created_at`
   - `test(scraper): add unit tests for date normalization`

2. **Атомарность**:
   - Один логический шаг — один коммит. Не объединять в один коммит правки верстки, багфиксы парсера и обновление Dockerfile.
3. **Чистота репозитория**:
   - Перед коммитом проверять `git status` и `git diff`.
   - **Запрещено коммитить**: файлы БД (`*.db`, `data/`), секреты и токены (`.env`), скомпилированные бинарники (`server`), временные файлы тестов (`/tmp/*`, `*.test`).

## 5. Работа с контейнеризацией и Docker

1. При добавлении новых системных утилит (например, `yt-dlp`, кодеки и т.п.) обязательно добавлять их в стадию выполнения `runner` в `Dockerfile` через `apk add --no-cache ...`.
2. После изменения кода, шаблонов или Dockerfile контейнер пересобирается и тестируется:
   ```bash
   docker compose up -d --build
   ```
3. Проверять логи контейнера на отсутствие паник и ошибок старта:
   ```bash
   docker logs metacrawler --tail 30
   ```

## 6. Чек-лист для агента перед сдачей работы

- [ ] Требование пользователя полностью выполнено и перепроверено.
- [ ] Все новые функции и граничные случаи покрыты юнит-тестами.
- [ ] Команда `go test -v ./...` завершилась без ошибок (`PASS`).
- [ ] Сервис проверен вживую (через HTTP-запросы `curl` или в браузере).
- [ ] В коде нет временных отладочных `print` / `fmt.Println`, не относящихся к логгеру.
- [ ] Рабочая копия Git проверена (`git status`), изменения закоммичены согласно Conventional Commits.
- [ ] Создан или обновлен отчет `walkthrough.md`.
